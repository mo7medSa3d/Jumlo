## Findings

### PD-01 — High — Direct download restart recovery cannot discard stale partial state

Evidence: `data/processing/DownloadOperationHandler.kt:111-119` keeps `<index>.part` and properties; line 115 rejects changed URL digest. `core/ResumePolicy.kt:18-30` rejects changed validators, non-206 and mismatched final metadata. `ui/downloads/DownloadsScreen.kt:237-243` offers URL re-entry for DOWNLOAD_RESTART_REQUIRED; `ui/AppViewModel.kt:555-561` merely replaces the memory secret and retries the **same job**. `data/jobs/JobStore.kt:92-112` retains job/partial state; cleanup is only cancellation/success.

Proposed device/server case: begin a direct download, interrupt after bytes, then change server ETag or have it ignore Range. Resume enters DOWNLOAD_RESTART_REQUIRED. Re-enter the same URL and retry: same stale offset/validator rejected again. Re-enter a fresh signed URL: line 115 rejects URL digest again. Expected an explicit restart that resets only the failed item's partial/journal; actual same-job retry has no reset transition. Creating a wholly new job can work around it. Static control-flow finding; no live server/device run.

### PD-02 — High — Paused direct files without validators become permanently nonresumable in the same job

Evidence: `core/StreamTransfer.kt:65-70` requires a resume validator before opening a response for offset>0; error is MISSING_RESUME_VALIDATOR, not RestartRequired. `data/processing/DownloadOperationHandler.kt:311-315` makes it an item failure. `data/jobs/JobStore.kt:177-179` and DownloadsScreen URL-reentry list do not recognize that code. Direct handler never resets no-validator partials; contrast `data/media/NativeDirectMediaRuntime.kt:211-217`, which deliberately resets such native-media fragments.

Proposed case: HTTP file responds with no ETag/Last-Modified, pause after any bytes, resume. Expected restart from zero when byte resume is impossible; actual FAILED/MISSING_RESUME_VALIDATOR, repeated retry repeats failure. Static finding, unexecuted on Android.

### PD-03 — High — Image compressor and Target Size can publish a larger or over-target result as success

Evidence: `data/processing/BitmapTransforms.kt:148` sets minimum target to 512 bytes; lines 154-185 try finite qualities and scales (minimum scale 0.28, minimum dimensions 16); **186-187 unconditionally copy bestSmallest and return**, with no target/original comparison. `ImageOperationHandler.kt:73-82` and `:285-290` publish this result; OutputStore.inspect checks image dimensions, not target.

Proposed cases: tiny optimized PNG converted by Compress Images into JPEG, or noisy high-resolution photo at Target Size 1000 bytes. If no tried encoding fits, expected truthful cannot-meet-target result or verified fallback; actual CREATED/completed with whichever candidate was smallest, even above original/target. Does not overwrite original. Source-level guarantee violation proven by unconditional branch; concrete encoder result remains device-dependent. Download image compression separately does compare original vs candidate (`DownloadOperationHandler.kt:264-267`) and can preserve original, so do not generalize the missing final gate to that publication branch.

### PD-04 — High — Shared decoder silently lowers dimensions and weakens comparison/resizing semantics

Evidence: `BitmapTransforms.kt:42-49` powers-of-two samples until pixels <= max(budget,16MiB)/8, with no reported warning/scale. `ImageOperationHandler.kt:55-65` computes percentage/longest-edge from this sampled bitmap. `BitmapTransforms.kt:89-91` further clamps requested dimensions. `ImageOperationHandler.kt:310-314` reports comparisons/dimensions on decoded samples. PDF page rasterization similarly silently reduces requested DPI (`PdfOperationHandler.kt:542-551`).

Deterministic arithmetic example: 8000x6000, maxBitmapBytes=128 MiB gives pixel allowance 16,777,216; decoder selects sample=2 -> about 4000x3000. Convert is no longer 8000x6000. Resize 50% becomes about 2000x1500, not 4000x3000. At lower heap budgets loss is larger. Large images with small distinguishing details may compare identical after subsampling; actual decoder/filter behavior requires pixel fixtures. Expected original-size conversion and resize relative to original metadata, or explicit user-visible resolution reduction and truthful compare label.

### PD-05 — High — Bitmap work budget is not a memory bound; visible adjust/join paths can OOM

Evidence: `BitmapTransforms.kt:207-215` watermark methods allocate full output copies and ignore budget; `:258-260` Adjust & Pad allocates `(width+2*pad)*(height+2*pad)*4` ignoring budget; `:111-128` encode accepts but does not inspect budget and may allocate a second full matte. `:236` join coerces budget to at least 16 MiB and budgets output alone, ignoring resident input list. `ImageOperationHandler.kt:194-207` holds copied bitmap for every join source; decoding can transiently hold original+copy. `OperationDispatcher.kt:26-28` serializes img/pdf jobs but dl_02 image/PDF conversion bypasses that bitmap semaphore and can run concurrently with them.

Arithmetic: 4000x3000 decoded source + allowed pad=2000 yields 8000x7000 output = 224,000,000 bytes (~214 MiB), plus ~46 MiB input, before encoding, exceeding common heaps and 128 MiB work budget. Expected bounded tile/scale or explicit resource failure before allocation. JobStore catches OutOfMemoryError at :173-175 but that is failure after allocation, not prevention.

Fresh test caveat: existing Android `data/ImagePixelTest.kt:26-32` expects IllegalArgumentException for join of two 10x10 bitmaps with budget 1000; current `BitmapExtras.join` does not throw and its code produces 20x10. Static contradiction found; **test not run** in this subaudit.

### PD-06 — High — PDF form parser cannot enter numeric/boolean strings into text fields

Evidence: `PdfOperationHandler.kt:71-78` infers every int-parsable string as FormEntry.Radio and `true`/`false` as FormEntry.Check, including JSON **quoted strings**; `PdfBoxBackend.kt:270-280` requires matching field type.

Proposed fixture: AcroForm PDTextField `age`; fill `age=42` or `{"age":"42"}`. Parser creates Radio(42); backend requires PDRadioButton and fails FORM_FIELD_TYPE_MISMATCH. Similar `active="true"` text field fails. Expected strings preserved for text fields and values parsed according to target field type (or explicit typed schema). Entire publication fails without mutating source. Static deterministic type mismatch; no handler/device execution.

### PD-07 — High — Form flatten can erase values when widget appearances or page references are missing

Evidence: `PdfBoxBackend.kt:295-299` silently skips widgets without widget.page; `:304-305` removes widget annotations; `:308-309` skips missing normal appearance or rectangle; `:323-324` unconditionally drops document AcroForm and saves. No verification of visual/value preservation. Handler publishes via generic PDF page-count inspector (`PdfOperationHandler.kt:365`, `OutputStore.kt:144-148`).

Proposed fixture: AcroForm with existing value and widget lacking normal appearance; choose flatten without changing values. Expected regenerate or fail safely retaining fields; actual annotation can be removed before appearance check and AcroForm always removed, producing valid nonempty PDF with field content absent. Missing widget.page similarly omitted. Existing `PdfStructureCoreTest.fill_form_and_flatten` covers one ordinary generated fixture, not these cases. Source-level data-loss branch; fixture/device rendering pending.

### PD-08 — High — Manual scanner quad uses wrong coordinate space over letterboxed image

Evidence: `ui/scan/ScanScreen.kt:298-301` photo ContentScale.Fit inside full box, but drag normalization at :307-315 and handles at :322 normalize the full box. `perspectiveQuad` :250-254 multiplies these fractions by source image dimensions. No fitted-image offset or size conversion.

Proposed case: capture portrait page and view in wide/short preview box; place corners exactly on the displayed document edges, apply. Expected crop matches selected visible rectangle; actual selected fractions include letterbox regions so source coordinates differ. Example: 300x340 box with 3:4 image is width 255, x offset 22.5; source x=0.1 appears at screen x=48 -> UI records 0.16 and crops x=0.16. Error grows with aspect mismatch. Static geometry proof; Android touch/render repro pending.

### PD-09 — Medium — CameraX manual scan ignores capture EXIF orientation

Evidence: `ScanScreen.kt:231-241` BitmapFactory decode has no ExifInterface or orientation transform; :244-271 perspective output JPEG strips metadata. This differs from correctly EXIF-normalizing `BitmapTransforms.decode` :54-68.

Proposed fixture/device: camera JPEG stored in sensor orientation with EXIF rotate 90 or 270. Expected upright preview/corrected page; actual raw pixel orientation shown and re-encoded permanently without orientation metadata. Conditional on camera storage behavior. Static missing-normalization observation, real camera case pending.

### PD-10 — Medium — Successful imported snapshots have no user deletion or retention policy

Evidence: `SourceStore.kt:51-69` copies every imported document into app files/inbound with new UUID (even persisted grants/repeated URI); source deletion API at :92-100 is called only for rollback in `AppViewModel.kt:309,417`. `FilesScreen.kt:245-250` imported rows only offer add to workspace. `AppViewModel.kt:232-233` remove/clear queue only alter draft IDs; cleanup at :658-664 only touches cache. No DAO jobs-history delete either (`ProcessingEntities.kt`).

Proposed case: repeatedly import multi-GB PDFs, finish jobs, remove from workspace, purge generated outputs and run cleanup. Expected some explicit way to delete unneeded owned input copies; actual all successful inbound snapshots persist until app data uninstall/clear. They appear in storage accounting (:673), so storage accumulation is visible but cannot be remedied in app. Not source-original deletion/data loss; an app-storage retention/management gap.

## Data/store/workflow architecture and limitations

- Room version 2 has sources/jobs/outputs/drafts plus legacy managed_files/download_tasks. Non-destructive 1->2 migration creates new tables/indexes (`data/local/DatabaseMigrations.kt`); root owns schema/build verification. Legacy fullUrl gets redacted on every open (`LegacyDownloadPrivacyCallback.kt`).
- New imports are immutable private disk snapshots. Imports do not impose artificial 4 GiB limit (Long.MAX_VALUE disk-bounded); reuse cached file avoids second seek copy. Max input count per job 1000, serialized settings <=100000 chars, UUID/schema validation.
- Source snapshots have SAF URI/grant flags metadata, owned snapshot path validation/symlink protection, cancellation-aware 64 KiB import loops, sync+atomic move, and rollback for failed handoff. Zero-byte provider import can be recorded but SourceSnapshotPolicy rejects zero length on read; archive extraction itself supports legitimate empty members. No source health/GC service.
- Room jobs store immutable request and snapshots; WorkManager unique work by job UUID; lease owner/fenced mutations and heartbeat every 15s with 60s lease, foreground promotion best effort. Pending recovery schedules QUEUED/VALIDATING/RUNNING/FINALIZING/INTERRUPTED when no active lease. Paused stays paused. Retry retains logical job/output keys, preserves completed publications.
- Progress/outcomes are not transactionally appended per published item during handler execution; final outcome list saved when handler returns. Already published outputs are authoritative in OutputStore even if worker interruption yields incomplete snapshot until retried.
- Cancel supports QUEUED/VALIDATING/RUNNING/FINALIZING/INTERRUPTED/PAUSED only, not WAITING_FOR_INPUT/FAILED/PARTIAL, and UI exposes no cancellation for those states. Retained partial data for failures can remain without dedicated history cleanup. Retry can fail JOB_NOT_RETRYABLE if caller arrives while lease held; paused/interrupted/waiting paths wait up to 2 seconds.
- Download max concurrency DataStore preference applies to admission gate, 1–6. Jobs each capture limit when admission begins. Wi-Fi/unmetered policy checked on every transfer read callback; WorkManager CONNECTED/UNMETERED constraints; Wi-Fi requires actual WIFI transport, not merely unmetered.
- URLs/passwords are session-only in EphemeralSecretStore ConcurrentHashMap. Cold process restarts intentionally need URL re-entry; Room persists opaque handles. Draft secrets stripped. This privacy tradeoff prevents unattended cold-start URL resumption. Cookies live WebView jar; headers memory-only; UA/desktop setting persisted. Native transfer uses host-scoped cookies at redirect hops.
- Standard media runtime has no yt-dlp runtime, HLS/DASH, JS site extraction, mux or audio conversion. Optional media flavor invokes pinned APK resources and native executables, process-group cancellation/timeouts/stdout limits, selected formats; arguments include retry=2/fragment-retries=2, --continue, --abort-on-unavailable-fragments, --hls-prefer-native. DASH depends on yt-dlp-selected formats. No live site guarantee or authentication extraction qualification. PackagedMediaRuntime intentionally does not use session cookies/custom headers (`app/src/media/.../MediaRuntimeFactory.kt:64-69,135-160`), so WebView login does not authenticate yt-dlp.
- Direct StreamTransfer: at most 10 redirects; HTTPS downgrade rejected; identity encoding request, gzip decoding only for first download; known-length completion/overflow checks; strict If-Range/ETag/last-modified/final URL digest; up to 3 automatic retries with exponential backoff **only while no new bytes were written**. Unknown-length streams cannot prove semantic completeness. Outputs have SHA-256 generated after download, but no expected server digest setting; generated digest proves stored bytes stability, not equivalence to remote intent.
- Budget limits: input Long.MAX_VALUE constrained by free space, private downloads 16 GiB, native direct media hardcoded 8 GiB, optional media workspace 16 GiB, archive expanded 4 GiB/2048 entries/depth32, individual published page outputs 512 (PDF fan-out ZIP fallback), ZIP extract 512 files (no large-fanout archive fallback). Output/compression/PDF save paths often rely on filesystem errors rather than explicit mid-write free-space checks; snapshots+staging+best/candidate+public mirror can require several copies.
- Output publication: validate stage, sync/hash, atomic durable journal, atomic move, hash verification, Room insert reconciliation. Private authoritative output plus independently hash-verified SAF/MediaStore mirror; mirror failures caught and publicUri=null, Files screen displays fallback warning. Save As streams and re-reads SHA-256; on failure correctly warns target may be partial. Output rename is not in-place available; batch rename produces copies.
- Recovery validates every journaled historical private file. `DurablePublication.reconcile:97-101` hashes all results through finish:83, called at startup and **before each job** (`JobStore:142`); OutputStore.reconcile also calls find which hashes again. Large history means latency proportional to total saved bytes before unrelated work. A single corrupt historical journal/result throws globally, no quarantine; this can block reconciliation/jobs. A resilience/performance risk from source, no real corruption fixture run.
- Managed trash journals intent before move, verifies bytes, recovers interrupted move/restore, moves original publication journal out so trashed outputs do not resurrect, exact confirmed ID purge with symlink checks. Private copy survives public mirror deletion errors. Undo IDs are ViewModel memory and snack action; durable trash restore exists after restart. Provider delete is permanent and separate from managed trash.
- Preferences use atomic DataStore edits: theme/language/motion/haptics/sounds/file view/accent/font/default Wi-Fi/destination/max downloads/quick actions/recent+most-used/favorite output IDs/onboarding/notification status. SAF tree is separate committed SharedPreferences. Favorite IDs can outlive permanent output purge (orphan metadata); no practical file-data harm. Presets are hardcoded UI choices whose selected values persist in one workspace draft; no named saved preset repository.
- Workspace checkpoint+recovery draft transaction, 300ms autosave debounce, sanitized secrets, durable submission fingerprint/request dedup; URLs not saved with draft. Explicit saved draft and recovery separate. No multi-document project/draft browser or editable history deletion API.
